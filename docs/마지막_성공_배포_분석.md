# 마지막 성공 배포 분석 및 원인 파악

## ✅ 마지막 성공 배포 (커밋: 0c5b1c5)

### 성공한 워크플로우 특징

**단순하고 직접적인 구조:**
```yaml
1. GCR 인증: gcloud auth configure-docker gcr.io -q
2. 빌드: docker build -t ${IMAGE} .  (루트에서 빌드)
3. 푸시: docker push ${IMAGE}
4. 배포: gcloud run deploy (RAILS_MASTER_KEY 포함)
```

**핵심 차이점:**
- ✅ **단순함**: GCR만 사용, fallback 없음
- ✅ **루트 빌드**: `docker build -t ${IMAGE} .` 
- ✅ **RAILS_MASTER_KEY 전달**: `--set-env-vars`에 포함
- ✅ **workflow_dispatch만**: push 트리거 없었음 (또는 추가됨)

## ❌ 현재 워크플로우의 복잡성

**추가된 복잡성:**
- GCR 시도 → Artifact Registry fallback
- 파일 기반 상태 전달 (`/tmp/docker_image.txt`)
- 조건부 실행 (`if: failure() && steps.gcr_push.outcome == 'failure'`)
- 환경 변수 전달 로직 추가

## 🔍 문제 원인 분석

### 1. 근본 원인
**`GCP_PROJECT_ID` Secret이 비어있었음** → 모든 단계 실패

### 2. 부수적인 문제
- 불필요한 복잡성 추가
- Fallback 로직이 오히려 문제를 숨김
- 원래 작동하던 단순한 구조를 복잡하게 변경

## ✅ 해결 방안

**원래 성공했던 방식으로 되돌리기:**

1. **단순한 GCR 사용** (원래 방식)
2. **fallback 제거** (불필요한 복잡성)
3. **루트 빌드 컨텍스트 유지** (현재도 `.` 사용 중 - OK)

### 원래 성공했던 워크플로우 구조

```yaml
steps:
  - Configure Docker auth (gcr.io)
  - Build and push image (gcr.io)
    - IMAGE=gcr.io/${PROJECT_ID}/${SERVICE}:$(git rev-parse --short HEAD)
    - docker build -t ${IMAGE} .
    - docker push ${IMAGE}
  - Deploy to Cloud Run
    - --set-env-vars=BASE_URL=${BASE_URL},RAILS_MASTER_KEY=${RAILS_MASTER_KEY}
```

**핵심:**
- ✅ 단순함
- ✅ GCR 직접 사용
- ✅ Secrets 올바르게 설정되어 있어야 함
